# Тестовое задание

## Правила

- Покупатель без логина пропускается.
- Покупатель ищется по CRM id, иначе по логину среди сделок; неоднозначный
  логин не используется.
- Сделка ищется по CRM id, иначе по логину среди покупателей. Если нашлись две
  разные записи, они сливаются в найденную по сделке, вторая удаляется.
- После успешного полного прохода удаляется всё, чего не было в выгрузке,
  включая сущности с «удалить» в имени.
- При прерванном сборе чистка не запускается.
- Схема поддерживает поиск по точному логину и названию и связь сделка-покупатель.

## Что было дорого

Старый вариант делал `SELECT` по JSONB (`@>` без GIN-индекса), `INSERT/UPDATE`
и `commit` на каждую сущность. В конце он читал всю `abstract_customer` с JSONB
в ORM и отдельно проходил каждый агрегат. Плюс `sleep(1)` на каждой странице CRM.

Оценка на 20k/50k:

| | Было | Стало |
|---|---|---|
| Запросы | ~350–400 тыс. | ~1 тыс. |
| Commit'ы | ~150 тыс. | ~140 |
| Память | 0,6–1,5 ГБ | 10–20 МБ |

После изменений — батчи по 500, ~280 страниц CRM по 250 записей, память
ограничена размером пачки.

## Что изменено

- **Схема.** JSONB-массивы заменены таблицами `amo_customers`, `amo_leads`,
  `amo_contacts`, `amo_companies`, `send_methods`. Поисковые поля — обычные
  колонки `crm_id`, `login`, `name` с индексами, `sync_run_id` — для чистки.
  `abstract_customer_id` — FK с `ON DELETE CASCADE`.
- **Батчинг.** `chunked` и `upsert_rows`: один `INSERT ... ON CONFLICT DO UPDATE`
  на пачку и один commit на пачку. Новые агрегаты создаются пачкой через `nextval`.
- **Слияние.** `build_merge_map` разворачивает цепочки слияний, строки переносятся
  группой SQL-запросов. Актуальная строка не перетирается устаревшей.
- **Чистка.** Полностью set-based по `sync_run_id`, без чтения JSONB.
  Запускается только после успешного завершения обоих циклов.
- **Клиент CRM.** Ответы разбираются через `Customer.from_dict` / `Lead.from_dict`,
  контакты сделок попадают в БД, пустые `_embedded` и `_links` не роняют прогон,
  пагинация идёт по курсору, на 429/5xx/сеть есть backoff.

## Что исправлено

- `AttributeError` на `get_schema`/`as_dict`.
- `KeyError` на пустом `_embedded` и отсутствующем `_links.next`.
- `Lead.contacts` никогда не заполнялся.
- Падение старого фильтра на `name = None`.
- Чистка запускалась после исключения в сборе.
- Дубли CRM id внутри пачки создавали лишние агрегаты.

## Что оставлено

- Публичная точка входа и сигнатура `collect_leads_customers(is_full=True)`.
- JSONB `data` с прежним форматом `general`/`api_value` — для существующих читателей.
- Константы статусов `111349` / `143` и одиночные хелперы (`lead_action`,
  `create_or_update_*`, `filter_*`) — для совместимости.
- `send_methods` не собираются этим прогоном, но переносятся при слиянии.
- `requests` и текущий клиент CRM — без новых зависимостей и сервисов.

## Допущения

- CRM отдаёт до 250 записей на страницу, пагинация — по `_links.next`.
- Ключ кастомного поля — `field_name` (например, «Логин»).
- CRM id у покупателей и сделок есть; вложенные сущности без id сохраняются,
  но не дедуплицируются между частичными прогонами.
- Покупатель без логина не создаётся и не
  обновляется; его прежняя запись удаляется полной чисткой.
- `is_full=False` не запускает чистку.
